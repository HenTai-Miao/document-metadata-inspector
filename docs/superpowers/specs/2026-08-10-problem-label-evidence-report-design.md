# 问题标签证据清单结果页设计

## 状态与适用范围

- 日期：2026-08-10。
- 产品：离线桌面应用“文档元数据核验”。
- 页面：正式核验结果页。
- 状态：视觉 Mock 已由用户确认，开始前端实现。
- 本规格取代同日“风险项 × 涉险公司矩阵报告”在结果页上的展示方案；旧规格不再是本页面的实现依据。
- 本次只修改 Electron 结果页的数据视图、DOM、样式和对应测试，不改变 Python 比较算法、报告 JSON、扫描 IPC、目录选择、扫描进度或元数据明细页面。

## 页面目标

结果页必须同时回答三件事：

1. 11 类检查分别是否发现风险。
2. 有风险时命中了哪些值。
3. 每个命中值涉及哪些公司组合，以及双方分别有哪些证据文件。

页面不使用顶部问题标签 Tab，不把不同问题标签藏在切换交互后面。11 个标签全部在同一页面中按固定顺序纵向展示。

## 固定问题标签

问题标签是一个有序、封闭的展示集合：

| 顺序 | 比较字段 | 页面名称 |
| --- | --- | --- |
| 1 | `author` | 创建人检测 |
| 2 | `last_modified_by` | 修改人检测 |
| 3 | `comment_author` | 批注人检测 |
| 4 | `revision_author` | 修订人检测 |
| 5 | `manager` | 经理检测 |
| 6 | `company` | 公司检测 |
| 7 | `signer_identity` | 签名人检测 |
| 8 | `username_path_trace` | 路径用户名检测 |
| 9 | `template` | 模板检测 |
| 10 | `created_at` | 创建时间检测 |
| 11 | `modified_at` | 修改时间检测 |

兼容比较器已经归一化的别名：

- `annotation_author` 归入 `comment_author`。
- `signature_signer_name` 归入 `signer_identity`。

页面标题可以概括为“11 类检查标签”，但每个卡片标题必须使用完整格式，例如“问题标签：创建人检测”。

## 信息层级

每个有风险标签严格使用以下层级：

```text
问题标签：创建人检测                有风险
2 个命中值 · 3 组公司关系

  命中值  李建国
  2 组公司关系

    公司 A ↔ 公司 B
      公司 A 的文件
        投标函.docx
      公司 B 的文件
        报价清单.xlsx

    公司 B ↔ 公司 C
      公司 B 的文件
        技术方案.pdf
      公司 C 的文件
        技术标.pdf

  命中值  zhangmin
  1 组公司关系

    公司 D ↔ 公司 E
      公司 D 的文件
        投标函.docx
      公司 E 的文件
        报价清单.xlsx
```

层级不可展平为“风险行 × 公司列”的矩阵，也不可把证据文件移入一个需要点击后才更新的公共侧栏。

## 有风险与无风险状态

### 有风险

一个问题标签关联至少一个跨投标人 trace 时显示为“有风险”：

- 卡片使用红色左边线和红色“有风险”状态标签。
- 卡片头部显示命中值数量和公司关系数量。
- 卡片主体完整展开命中值、公司组合和双方文件。
- 不需要点击、展开或切换即可读取全部证据。

### 无风险

没有关联 trace 的问题标签仍然必须展示：

- 使用与有风险标签相同的全宽卡片、标题区和内容区结构。
- 卡片使用绿色左边线和绿色“无风险”状态标签。
- 头部显示“0 个命中值 · 0 组公司关系”。
- 内容区显示绿色核验结果“无风险”，并说明未发现跨公司相同值。
- 不把无风险标签集中成九宫格、标签条或独立折叠区。

页面顶部显示“有风险 N”和“无风险 M”，且 `N + M` 必须等于 11。

## Trace 到问题标签的归类

结果页继续消费现有 `ScanResult.personTraces` 与 `ScanResult.cautionTraces`，不改变后端判定。

每个 trace 按 `fieldNames` 归入一个或多个问题标签：

- 单字段 trace 进入对应标签。
- 多字段 trace 同时进入每一个对应标签。
- 例如一个 trace 的 `fieldNames` 是 `author` 与 `last_modified_by`，该命中值及其完整证据同时出现在“创建人检测”和“修改人检测”下。

这种多标签复用与已确认 Mock 一致，且保留比较器“同一身份值可跨不同元数据字段命中”的语义。页面不根据字段名称拆分或猜测后端证据。

同一问题标签内按命中值分组；相同显示值的 trace 合并其公司和文件证据，同时保持 trace 的输入顺序作为首次出现顺序。

## 公司组合与文件证据

### 公司顺序

只使用 `ScanResult.groups` 中 `kind === "bidder"` 的组。公司顺序严格遵循 `ScanResult.groups`，不按名称重新排序。

### 公司组合

对一个命中值实际涉及的投标人组生成无向公司组合：

- 两家公司生成一个组合。
- 三家公司生成三个不重复组合。
- 组合按公司原始顺序稳定生成。
- `A ↔ B` 与 `B ↔ A` 视为同一组合，只展示一次。

### 双方文件

每个公司组合下必须分别展示左右公司的文件：

- 文件只来自当前 trace 的 `documentIds`。
- 文档按其所属 bidder 组归到对应公司。
- 文件顺序沿用该组的文档顺序。
- 同一公司内重复文档 ID 只展示一次。
- 只显示文件名，不显示绝对路径、内部文档 ID、正文、批注正文或原始异常。

如果 trace 表明存在跨公司风险，但部分文档无法映射：

- 保留仍可映射的公司和文件。
- 不泄露无法映射的内部 ID。
- 某一侧没有可显示文件时写“暂无可显示文件证据”，不能把该标签降级为无风险。

如果 trace 无法形成任何可显示公司组合，问题标签仍显示“有风险”，并在命中值下显示“风险关系缺少可显示的投标人文件证据”。

## 页面结构

结果页从上到下为：

1. 页头：核验结果、11 类检查标签、根目录、核验时间。
2. 汇总状态：有风险数量、无风险数量；可附公司关系和证据文件统计。
3. 统一纵向问题标签清单。
4. 既有报告签名：核验人、核验日期、报告编号。

顶栏继续使用既有“选择目录 / 风险关系 / 元数据明细 / 重新核验”，本次不修改导航语义。

## 视觉规则

- 使用当前应用的系统中文字体和既有设计变量。
- 页面主体保持浅色柔光页头到白色内容区的过渡。
- 所有问题标签是同一种全宽卡片，不为无风险标签另造布局。
- 有风险使用 `--red` / `--red-light`；无风险使用 `--green` / `--green-light`。
- 命中值使用橙色弱底和等宽字体，表达“被比较的原始证据值”。
- 公司组合使用蓝色弱底；双方文件使用白底细边框标签。
- 风险卡片和无风险卡片均不使用重投影；结构主要依靠边框、弱底和间距。
- 不使用矩阵、深色证据侧栏、顶部标签页、折叠面板、悬浮弹层、图表或装饰性动画。
- 状态含义同时使用文字和颜色，不能只依赖红绿颜色。

## 响应式规则

- 桌面宽度下，公司组合、左侧公司文件、右侧公司文件组成三列。
- 宽度不足时三列按“公司组合 → 左公司文件 → 右公司文件”顺序纵向堆叠。
- 标签标题、状态和计数允许换行，不能截断完整问题标签名称。
- 页面本身不产生横向滚动。
- 正式验收尺寸：1440×900、1280×800、1024×720。

## 代码边界

### `desktop/src/renderer/render-result.ts`

- 用纯函数 `buildProblemLabelReportModel()` 将 `ScanResult` 转换为固定 11 标签模型。
- 模型负责字段归类、命中值合并、公司组合、双方文件和汇总计数。
- `renderResult()` 只根据模型建立统一纵向 DOM。
- 保留已有 `tField()`、扫描时间、报告签名和 `connectionTracks()` 回归接口。
- 移除结果页矩阵和联动证据侧栏的 DOM 构建，但不改其他 renderer 页面。

### `desktop/src/renderer/styles.css`

- 只替换当前结果页 `.rm-*` 样式块。
- 保留目录选择、扫描页、元数据明细、顶栏和底部状态的现有样式与本地改动。

### 测试

- `desktop/tests/render-result.test.ts` 测试纯模型。
- 当前合成浏览器测试改为验证统一标签证据清单，不再断言矩阵和侧栏。
- 真实运行时测试允许结果页出现有风险标签或 11 个无风险标签，但不能再查找矩阵元素。

本次不修改共享 JSON 模型、Python 比较器、Java worker、报告导出格式或 Electron IPC。

## 单元测试要求

纯模型至少覆盖：

1. 固定返回 11 个问题标签且顺序正确。
2. 标签名称全部带“检测”后缀。
3. 多字段 trace 同时进入创建人检测和修改人检测。
4. 有命中的标签按显示值分组。
5. 三家公司生成三个稳定、不重复的公司组合。
6. 每个组合双方文件来自正确 bidder 组。
7. 重复文档 ID 不重复展示。
8. 根目录文件和不属于 trace 的文件不进入证据。
9. 没有 trace 时 11 个标签全部为无风险，而不是返回空页面。
10. 缺失文档映射不泄露内部 ID，也不会把已有风险误标为无风险。

## 浏览器验收要求

1. 页面同时出现“问题标签：创建人检测”和“问题标签：修改人检测”。
2. 有风险标签完整显示命中值、公司组合和双方文件。
3. 无风险标签使用相同全宽卡片并显示“无风险”。
4. 页面总计恰好 11 个问题标签卡片。
5. 页面中不存在旧风险矩阵、深色证据侧栏或顶部问题标签 Tab。
6. 1440×900、1280×800、1024×720 无遮挡和页面级横向溢出。
7. 控制台无错误。

## 完成定义

用户进入正式核验结果页后，无需点击即可从上到下检查全部 11 类问题标签。每个有风险标签都能沿“命中值 → 公司组合 → 双方文件”追溯证据；每个无风险标签都以相同卡片结构明确写出“无风险”。页面名称全部使用“××检测”后缀，并通过单元测试、类型检查、格式检查、构建和真实浏览器截图验证。
