# 文档元数据核验 Electron 桌面端设计

## 状态与已确认范围

- 日期：2026-08-05
- 本设计把已经确认的两页流程落成真实 Electron 应用，不再制作独立 mock 页面。
- 只修改 `document-metadata-inspector/`，不修改父目录中的其他项目。
- 桌面端使用 Node.js、Electron、TypeScript 和 Vite；元数据提取继续调用现有 Python/Java/ExifTool 离线核心。
- 本轮用下载到桌面的 8 个公开原始 PDF、Word、Excel 文件完成真实演示和验收。

## 用户任务

审查人员选择一个“投标文件”根目录。根目录下面的每个一级子目录代表一个投标人，该目录内的文件属于同一投标人。程序扫描所有受支持文件后，只比较不同投标人之间的身份痕迹；同一投标人自己的文件不得互相判为冲突。

界面只分为两页：

1. 选择与扫描页：选择文件夹，展示识别到的投标人和文件数，提供“开始核验”和“停止”按钮，并在扫描时显示明确动画和当前状态。
2. 结果页：每个投标人以“图标和名称在上、文件内容在下”的证据卡展示。跨投标人的人员痕迹用红色文字和连接线显示；软件、模板等环境痕迹使用灰蓝色，不得伪装成人员相同结论。

## 产品语言与视觉方向

产品显示名使用“文档元数据核验”，项目和命令仍使用已确认的 `document-metadata-inspector` / `docmeta`。

视觉以“证据工作台”为主题：

- `ink` `#12233F`：标题和主文字。
- `cobalt` `#2855D9`：主要操作与扫描光束。
- `mist` `#EEF3FA`：窗口背景和分区。
- `paper` `#FFFFFF`：文件与投标人卡片。
- `trace` `#64748B`：软件、模板等环境线索。
- `danger` `#D92D3F`：仅用于跨投标人的人员身份痕迹。

中文标题使用系统可用的宋体/衬线字体栈，正文使用系统黑体字体栈，数据和摘要使用等宽字体栈。标志性元素是一束穿过文件卡片的垂直扫描光，扫描完成后转化为投标人之间的证据连接线。动画遵守 `prefers-reduced-motion`。

## 架构

### Electron 主进程

主进程拥有文件系统、目录选择和子进程权限。它提供窄化的 IPC：

- `selectFolder()`：只允许通过系统目录选择器选择一个目录，主进程保存不可由页面篡改的文件清单，并返回安全的目录摘要。
- `startScan()`：页面不传路径；主进程把已确认的普通文件逐个作为参数启动 `docmeta compare --group-by-top-level-dir --json`，禁止 shell 拼接和扫描时重新枚举。
- `stopScan()`：终止当前应用拥有的完整进程树，等待清理结束后才允许重新开始。
- `onScanProgress(listener)`：发送阶段状态，不暴露任意 IPC 通道。

开发时解析器优先使用已经构建的当前平台 `dist/<platform>-<arch>/onefile/docmeta`；正式包使用 `process.resourcesPath/docmeta-runtime/` 中随应用打包并校验的可执行文件。运行时同时对照应用代码中固化的预期哈希和资源清单，任一不一致都拒绝启动。不存在打包运行时时才在项目开发环境回退到 `uv run docmeta`，最终用户版本不得联网安装或依赖系统工具。

### Preload 安全桥

窗口保持 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`。Preload 使用 `contextBridge` 逐个暴露上述业务方法，不把 `ipcRenderer`、文件系统或进程 API 直接交给页面。

### 报告适配层

报告适配层是无 Electron 依赖的纯 TypeScript 模块。它将权威 JSON 和所选目录转换为小型页面模型：

- 用与 Python 核心相同的绝对路径 SHA-256 将重复文件名准确映射回投标人。
- 汇总文件状态、格式、证据数量、解析器数量和告警数量。
- `person_trace` 映射为红色高风险身份痕迹。
- `software_trace`、`organization_trace` 和 `document_environment_trace` 映射为中性环境线索。
- 未发现人员痕迹时明确显示“未发现跨投标人人员痕迹”，不制造演示冲突。

### Renderer

Renderer 是无框架的 TypeScript 单页应用，以有限状态机呈现：

```text
empty -> ready -> scanning -> result
                  |   |
                  |   -> failed
                  -> stopped -> ready
```

页面状态变化只由受信任桥接返回值驱动。结果页保留“重新选择”和“重新核验”，可展开查看每个文件的格式、解析器、证据量和告警。结果连接线使用 SVG，根据投标人卡片锚点绘制；人员线为红色，环境线为灰蓝色。

## 数据与隐私

- 页面可显示用户选择的根目录名称和相对文件名，但报告与日志不增加完整路径字段。
- 不把下载的真实文件或生成的真实扫描 JSON 提交到 Git。
- 临时报告写入操作系统临时目录，扫描结束或停止后删除。
- Electron 不加载远程页面，不启用 `<webview>`，内容安全策略只允许自身脚本和样式。

## 错误与停止行为

- 目录为空：停留在第一页，说明支持 PDF、Word、Excel。
- 目录没有一级投标人子目录：仍可扫描，但显示边界提示并把根目录文件归入“根目录文件”。
- 扫描部分成功：进入结果页并逐文件显示状态，不丢弃成功结果。
- 运行时缺失或损坏：显示明确的安装损坏/开发运行时缺失信息，不自动下载。
- 点击停止：终止当前子进程，状态回到可再次开始；不留下半成品报告。

## 跨平台与打包边界

Electron Forge 负责在各自原生系统生成安装包：Windows 使用 Squirrel，macOS 使用 ZIP/DMG，Linux 使用 DEB/RPM。各平台 CI 必须先调用现有 Python 构建脚本生成对应的 `docmeta` 离线运行时，再把该目录作为 Electron `extraResource` 打包。不能在 macOS 伪造 Windows/Linux 最终运行时。

## 验收标准

1. Electron 窗口能选择桌面真实测试目录并识别 2 个一级投标人、8 个文档。
2. 点击开始后真实启动现有三引擎核心，扫描中可停止，完成后进入第二页。
3. 实际结果显示 8/8 完成、3 个解析器/文件以及真实证据汇总。
4. 实际结果不出现红色人员冲突；`WPS 文字` 只显示为灰蓝色软件环境线索。
5. 同一投标人内部文件永远不会因完全相同字段单独产生红色连接。
6. TypeScript 单元测试、Renderer 浏览器自动化、Electron 构建和既有 Python 门禁通过。
